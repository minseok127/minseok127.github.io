# 그래프 모델

---

관계형 모델은 데이터를 행과 열로 구성된 2차원 테이블로 표현한다. 이러한 테이블을 relation이라고 하고, relation들의 집합이 데이터베이스를 구성한다. 이와 다르게 속성 그래프 모델은 데이터베이스를 다섯 가지 요소들로 구성한다. $G = (V, E, \rho, \lambda, \sigma)$로 적는다. $V$는 정점 (vertex) 집합, $E$는 정점들을 연결하는 간선 (edge) 집합이다. $\rho$는 간선을 입력으로 받고 출발 정점과 도착 정점 쌍을 반환한다. $\rho: E \rightarrow (V \times V)$로 적을 수 있다. 주의할 점으로 단사가 아니어도 된다. 즉 서로 다른 간선이 같은 정점 쌍을 반환해도 된다. 출발 정점과 도착 정점이 같은 self loop도 허용된다. $\lambda$는 입력으로 모든 정점과 간선, 즉 $V \cup E$를 받고 label을 반환한다. $\lambda : (V \cup E) \rightarrow label$로 적을 수 있다. Label은 정점들과 간선들을 그룹화하는 단위이다. $\sigma$는 개별적인 정점 혹은 간선에 추가로 속성을 입력으로 받는다. 그리고 이에 대응되는 속성 값을 반환한다. 즉 어떤 정점 혹은 간선의 특정 속성에 대한 값을 얻는다. $\sigma : (V \cup E) \times K \rightarrow \text{property value}$로 적을 수 있다. 주의할 점으로 모든 정점과 간선이 $K$에 속한 모든 속성을 가질 필요는 없다. 각각의 정점과 간선마다 서로 다른 $K$의 부분집합을 가져도 된다.

관계형 모델과 속성 그래프 모델이 가지는 주된 차이는 데이터 사이의 연결 방식이다. 관계형 모델에서 튜플들을 연결할 때는 쿼리에서 요구하는 속성들에 대한 조건을 검사하고 연결한다. 개별적인 튜플만 봤을 때는 이것과 연결되는 다른 튜플의 정보를 알 수 없고, 연결의 근거는 쿼리에서 정한다. 물론 foreign key처럼 스키마 정의 단계에서 연결 관계를 암시하는 방식이 있지만, 쿼리가 두 relation을 연결하기 위해서 foreign key를 사용하지 않을 수도 있다. 반면 속성 그래프 모델은 간선이 정점들 사이의 연결 정보를 담고 있다. 두 정점의 연결에 대한 근거를 쿼리로부터 얻지 않고, 데이터 삽입 단계에서 정한다.

그래프 모델의 정점은 두 개의 집합을 정의한다. 정점 $v$에서 나가는 간선 집합 $out(v)$와 $v$로 들어오는 간선 집합 $in(v)$이다. 다음과 같이 정의된다.

$$
\begin{aligned}
out(v) = \set{e \in E : \text{V에 속하는 어떤 정점 w에 대하여, } \rho(e) = (v, w)} \\
in(v) = \set{e \in E : \text{V에 속하는 어떤 정점 w에 대하여, } \rho(e) = (w, v)}
\end{aligned}
$$

쿼리 실행 과정에서는 정점을 이동하는 기본적인 연산에서 이 집합들을 사용한다. 그리고 필요에 따라 $\lambda, \sigma$를 사용하여 정점 혹은 간선을 필터링한다. 그런데 간선 방향을 따라 이동할 때는 out만 필요하지 않나? in은 왜 필요한걸까? 알아보니 크게 세 가지 이유가 있는데, 첫 번째로 어떤 정점으로 들어가는 정점이나 간선을 찾고 싶은 경우이다. 만약 in이 없다면 모든 정점들의 out을 보면서 해당 정점을 찾아야 한다. 두 번째로 쿼리 옵티마이저가 봤을 때 출발 정점보다 도착 정점에 대한 selectivity가 낮으면, 도착 정점을 필터링하고 간선의 반대 방향으로 이동하는게 중간 데이터들이 더 적어질 수 있다. 세 번째로 쿼리가 방향을 무시하는 패턴을 요구할 수 있다. 이 경우 in, out이 둘 다 필요하다.

이번에는 그래프 모델에서 쿼리가 어떤 형태인지 보자. 2023년 SQL 표준에 SQL with Property Graph Queries (SQL/PGQ)가 추가됐다. 기존 관계형 데이터베이스의 데이터를 새로운 그래프 데이터베이스로 옮기는게 아니라, 이미 있는 테이블들에 그래프를 정의하고 그래프 쿼리를 보낼 수 있다. 

먼저 그래프 정의에 대한 예시를 보자. 다음과 같은 테이블들이 정의되었다고 치자.

```jsx
CREATE TABLE users   (user_id BIGINT PRIMARY KEY, name TEXT, joinDate DATE);
CREATE TABLE posts   (post_id BIGINT PRIMARY KEY, content TEXT, createdAt TIMESTAMP);
CREATE TABLE likes   (like_id BIGINT PRIMARY KEY, user_id BIGINT, post_id BIGINT, likedAt TIMESTAMP);
CREATE TABLE follows (follower_id BIGINT, followee_id BIGINT, PRIMARY KEY (follower_id, followee_id));
```

이에 대한 그래프를 다음과 같이 정의할 수 있다.

```jsx
CREATE PROPERTY GRAPH g
  VERTEX TABLES (
    users KEY (user_id) LABEL User PROPERTIES (name, joinDate),
    posts KEY (post_id) LABEL Post PROPERTIES (content, createdAt)
  )
  EDGE TABLES (
    likes KEY (like_id)
      SOURCE KEY (user_id) REFERENCES users (user_id)
      DESTINATION KEY (post_id) REFERENCES posts (post_id)
      LABEL Likes PROPERTIES (likedAt),
    follows KEY (follower_id, followee_id)
      SOURCE KEY (follower_id) REFERENCES users (user_id)
      DESTINATION KEY (followee_id) REFERENCES users (user_id)
      LABEL Follows
  );
```

VERTEX TABLES에 들어가는 users와 posts의 데이터들이 정점들이다. EDGE TABLES에 들어가는 likes, follows의 데이터들이 간선들이다. SOURCE KEY와 DESTINATION KEY는 간선의 출발 정점과 도착 정점을 나타낸다. LABEL은 레이블, PROPERTIES는 속성이다. 주의할 점으로 PROPERTIES가 지정되면 해당 속성만 있는 것이다. likes의 경우 위에서 정의한 테이블의 모든 속성들을 가지는게 아니라 likedAt만 가진다. 그리고 follows처럼 PROPERTIES가 없으면 해당 테이블의 모든 속성들을 가지겠다는 뜻이다. NO PROPERTIES라는 키워드를 쓰면 속성을 안가진다는 뜻이다.

이번에는 간단한 쿼리 예시를 보자.

```jsx
SELECT * FROM GRAPH_TABLE ( g
  MATCH (a IS User)-[IS Follows]->(b IS User)-[l1 IS Likes]->(p IS Post),
        (a)-[l2 IS Likes]->(p)
  WHERE a.name = 'kim'
  COLUMNS (b.name AS friend, p.content AS content)
) AS t;
```

쿼리가 요구하는 패턴은 두 가지이다. 첫 번째는 이름이 kim인 User 레이블의 출발 정점이 Follows 레이블인 간선을 통해 다음 User 정점과 연결되고, 다음 User 정점에서 Likes 레이블인 간선을 통해 Post 정점과 연결되는 것이다. 두 번째는 출발 정점이 Likes 레이블인 간선을 통해 첫 번째 경우와 같은 Post 정점과 연결되는 것이다. 두 가지 경로 모두 존재하는 경우들이 결과가 된다. 주의할 점으로는 항상 출발 정점에서 시작해서 마지막 Post 정점 방향으로 간다는 보장은 없다. 위에서 말한 것처럼 경우에 따라 반대 방향으로 갈 수도 있다.
